## 1. 问题（为什么枚举式补点已到边际为零）

探针与**被测插件**跑在**同一个进程**、**同一组输出面**上。于是「探针的结论」这件事本身，
是被测方**可写**的：

| # | 形态 | 现状 | 类别 |
|---|---|---|---|
| ① | 插件打印一条**伪造 marker**（`__DSH_PROBE__{ok:true,...}`） | nonce 带外通道（**stdin**）+ fd3 隔离**挡「无意的自我发绿卡」与「从环境块 / argv 反读」**；同进程同 uid 的其它篡改仍需进程级隔离 | 信任边界（R26） |
| ② | 插件 `setUncaughtExceptionCaptureCallback()` / `removeAllListeners` 静音探针防线 | 探针**收尾自检**可判定（`plugin.process_defense_tampered`，R28 起用身份检查 + 行为级 canary） | 信任边界 + 侧信道 |
| ③ | 插件同步占死事件循环 | 宿主 `SIGKILL` **有界**；但看门狗（探针内）**仍排不上** | 侧信道（R24 残留②） |
| ⑤b | 插件**先杀探针再伪造**（摘 `exit` 钩子 + `exit(0)` 抢跑） | **fail-open（本轮实测）**：fd3 为空 ⇒ 装配器**回退信任 stdout** ⇒ 带正确凭据的伪造行被采信（`ok=true`）。**通道选择不是关键**（写 fd3 / 写 stdout 等价），**「探针是否来得及 emit」才是关键** ⇒ 需「独立 fd 且永不回退 stdout」 | 信任边界（R26 残留②） |
| ⑤c | 插件把 **fd3 换成自己的文件** ⇒ 探针（不知情）把**带凭据的真报告**写进插件的文件 ⇒ 插件在 `exit` 钩子里读出凭据 ⇒ 伪造绿卡 + 压 `process.exitCode` | **v0.2.5 已收口（R26-R3′）**：旧实现（回显 nonce）判 `GREEN` 放行。⇒ **凭据保密性不是唯一防线**（凭据由探针**亲自**交出）。收口两条**并集**、**不依赖批 2**：**C′** 结果行不回显 nonce，改**正文绑定**认证标签（凭据不可迁移）；**D** 报告自称 fd3 而宿主实际 fd3 为空 ⇒ 判 `plugin.protocol_injection`（依据宿主侧观测，压退出码无效） | 信任边界（R26-R3′） |
| ⑤ | 插件猴子补丁 `JSON.stringify` 伪造绿卡（**v0.2.3 实测**，见 R29） | 探针**加载期捕获引用** + 装配器**退出码交叉**（两道并集）挡住本形态；**同时**改退出码仍可绕过（离线 [20] 双回退把它跑出来） | 信任边界（R29，与 R26 同族） |
| ④ | 插件在探针写报告前 `process.exit(0)`，再自补一条干净报告 | 出口③已闭合（探针自己的 `exit` 钩子记账）；「补报告」由 nonce/fd3 拦 | 信任边界 |

**共同根因**：报告（marker）与相位信标都走**被测插件可写的输出面**，且**凭据与被测方同进程**。
⇒ 这是**架构前提**问题，不是探针 bug；逐点补出口（已补 7 条）对该族**边际为零**（总师 §3-Q1 的判据）。

## 2. 目标与非目标（先划边界，避免「重做」变成无底洞）

**目标**：让「探针结论」与「被测插件的输出」**可区分**——即：插件**无法**在不被发现的前提下
伪造 / 改写 / 截断探针的结论。

**非目标**（显式声明，避免过度承诺）：
- ❌ **不做安全沙箱**：不防「插件消耗 CPU / 内存 / 网络」这类资源攻击（那是容器 / cgroup 的事）；
- ❌ **不防「插件本身是恶意代码」的全面对抗**：本中台的定位是**验收**（对**可信但可能写错**的插件）；
  重做只把「可信前提被打破」的**后果**从「静默假绿」降到「**可判定 / 可拒绝**」；
- ❌ **不改插件可见行为**（不要求插件改代码、不要求它配合握手）。

## 3. 两个候选方案

### 方案 A · **独立 fd 作真·带外通道**（+ 一次性 nonce）— **已落地**

| 项 | 内容 |
|---|---|
| 机制 | 宿主给探针开**第 4 个 fd**（`stdio: ['ignore','pipe','inherit','pipe']`）；探针把结果写 **fd3**（`writeSync(3, ...)`）。宿主**只信 fd3**，stdout 退化为纯日志 |
| nonce | 宿主 spawn 前生成随机 nonce（`randomUUID`/`randomBytes` 系），经 **stdin** 传（不进 argv / env）；marker 带 nonce，宿主校验逐字一致 |
| 结构不变量 | 「匹配前缀的结果行 ≥2 条 / 出现在 stdout」即判篡改（`plugin.protocol_injection`），**不采信任何一条** |
| 残留 | 插件**仍可**：① 读 env 拿 nonce（同进程）；② 写 fd3。⇒ **单独用 A 不足以闭合**，只是提高门槛 |
| 收益（已兑现） | ① 插件**误写 stdout** 不再污染判据；② 伪造需**主动**读 env + 写 fd3（从「顺手」变「刻意」）；③ 报告完整性不再受插件 stdout 噪声影响 |

### 方案 B · **进程隔离**（探针与被测插件分属两个进程）— **待立项**

| 项 | 内容 |
|---|---|
| 机制 | 宿主起**两个**子进程：`runner`（探针）与 `plugin-host`（真宿主 + 插件）。runner 经 **fd / IPC** 与 plugin-host 通信，**自己**汇总结果并写报告；插件在 plugin-host 里无论做什么（占死 / exit / 伪造 marker / 摘监听器）都**碰不到** runner 的报告通道 |
| 边界 | 插件仍与 plugin-host 同进程（它必须在真宿主里跑，才能验「装上就能用」）⇒ 能影响的只有**插件侧那一半**结果；runner 的判据字段（`hostFatal[]` / 完成位 / 相位）**不可写** |
| 成本 | **大**：拆探针为两段（宿主装配 vs 插件集成）、定义 IPC 协议与超时、离线回归台与 E2E 全改、看门狗语义重定义（占死时 runner 侧判「对端失联」⇒ **出口④ 才真正根治**） |
| 收益 | ① R26 的 ①③④ **同时**闭合（runner 的报告通道在**另一个进程**）；② R24 残留②（看门狗依赖被占满的事件循环）**根治**；③ 为后续「并行验多插件」留出结构 |

### 方案 C（推荐）· **A 已落地 → 只立项 B**

A 已在 v0.2.x 兑现；**剩下的根治工作 = B**。
